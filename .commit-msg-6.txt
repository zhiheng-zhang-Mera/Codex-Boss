P2-E: the road class, two declarations, and the two refutations that define what a road is not

Section 19 defines a road as a shared concern trapped inside a building and requires five proofs per
extraction; section 24 refuses count compensation; and CC-030 already measured one attempt to
relabel shared surface and refused it. So the class had to be built with that refutation as a
machine rule rather than as a convention.

The test has two halves. NECESSARY: the file is a LEAF -- imported across a capability boundary by
two or more capabilities and importing NO other capability. SUFFICIENT: the file carries NO POLICY
OF ITS OWN. Leafness is necessary and NOT sufficient, and that is the finding rather than a caveat:
two of the strongest candidates pass the leaf test and are refused.

  src/shared/execution.ts -- a leaf imported by four capabilities -- exports reviewResponse and
  defaultReviewPolicy, which DECIDE PASS, RETRY, HUMAN_REQUIRED or FAILED.
  src/shared/permission.ts -- a leaf imported by providers and tenx -- exports manifestAllows,
  manifestNarrow and desktopMutationGate, which is security's decision procedure.

A policy belongs to the capability that owns the outcome, so declaring either a road would HIDE an
inversion. Both are recorded as measured refutations, and the validator refuses a refutation for a
file that is not a leaf with at least two consumers: a record that records nothing is not evidence.

Two roads are declared, both leafless and policy-free: electron/commander/durable-json.ts (owned by
tenx, 17 consumers, 4 kernel edges, a durable-JSON primitive whose invariant is that a file is never
observed half written) and src/shared/input-object.ts (owned by tasks, 9 consumers, 3 kernel edges,
a pure contract by its own header).

The class is a DOWNSTREAM classification, not a fourth ownership class in the map: a road stays
physically inside its building, and that containment is the recorded debt, with an exit condition
naming the extraction that removes the declaration. That is what makes the arithmetic honest. The
first implementation did not do it and INFLATED the total from 801 to 828 -- every internal import
of the two roads became a phantom cross-capability edge. With the rule in place:

  kernel -> feature file edges   73 -> 66
  kernel -> feature pairs        25 -> 24
  mutual capability pairs        38 -> 34
  edges to roads                 -- -> 64   (published, not deleted)
  edges LEAVING roads            -- ->  0   (must be 0; a road with an out-edge is not a road)
  total cross-capability edges  801 -> 801  (unchanged, which is the point)
  files owned                   598 -> 598  (unchanged)

The four mutual pairs dissolved because in four cases a capability's ONLY dependency on another was
the shared file primitive, so the two were never in a cycle of implementation; both instruments
report 34, so the two measurements still agree.

The ratchet is lowered in this same commit, as its own IMPROVED line instructs, and gains the roads
rule: road_files and edges_to_roads are FLOORS, and any edge leaving a road FAILS.

Two more weaker gates were found on the way, both in this round's own work. The inspector's --verify
compared only the keys the INSPECTOR computed, so the inventory's two new road totals were never
asked about; it now iterates the UNION of both key sets and treats a key it cannot compute as a
failure. That closure immediately found THREE more keys it had never computed at all
(fullyDeclaredCrossCapabilityEdges, realPairsAlreadyDeclared, realPairsUndeclared). All twelve are
now cross-checked; the nine derivable from an edge list are additionally re-summarised from it.

Falsification: a road that imports a capability; a road with one consumer; a road owned by a KERNEL
(a gap the first version of the validator had, which the falsification case found); a road owned by
no capability; a declared owner disagreeing with the map; a road that is also a composition-root
file; a road missing each of the five proofs; a road citing a missing ledger entry; a classification
too thin to be a rule; a refutation for a non-leaf and for a single-consumer file; a file both
declared and refuted; plus the union-of-keys gate, and the anti-inflation invariant asserted
directly on the edges.
